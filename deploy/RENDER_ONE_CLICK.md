# One-click all-Render deployment (free plan)

**Everything runs on Render's free plan: website, API, PostgreSQL and Redis (Key Value).** No Supabase, no Upstash, no Vercel, no S3 bucket, no second provider account. One Blueprint creates and wires all four resources:

```text
Browser
  │ HTTPS
  ▼
pitstop-web   Next.js frontend + same-origin cookie BFF   (free Docker web service)
  │ HTTP over Render's private network (hostport reference)
  ▼
pitstop-api   Django REST API, migrations on startup      (free Docker web service)
  ├── pitstop-db     Render Postgres 16, free             (private-network access only)
  │     └── application tables + uploaded media rows (MEDIA_STORAGE=database)
  └── pitstop-redis  Render Key Value (Valkey), free      (private-network access only)
        └── shared throttle counters / replay cache
```

| Resource | Blueprint name | Plan | Role |
|---|---|---|---|
| Web service | `pitstop-web` | free | Next.js UI + BFF; sets HttpOnly cookies, refreshes JWTs server-side |
| Web service | `pitstop-api` | free | Django/DRF API; runs `migrate` before serving (`backend/start-render.sh`) |
| Postgres | `pitstop-db` | free | Users, sessions, messages, diagnoses, bookings, AI budgets **and uploaded media** |
| Key Value | `pitstop-redis` | free | Shared rate-limit counters and idempotency/replay cache |

## 1. Deploy

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/EvilSnIzer/Pitstop)

1. Sign in to (or create) a Render account, then click **Deploy to Render** above — or in the dashboard use **New → Blueprint**, pick this repository, and accept `render.yaml`.
2. The Blueprint shows the four resources it will create. The only field it may prompt for is **`GEMINI_API_KEY`** on `pitstop-api`:
   - Paste a backend-only Gemini key to enable AI media analysis and final diagnosis, **or**
   - Leave it empty. The app still runs: deterministic intake works, media analysis adds an explanatory note, and diagnosis returns `ai_not_configured` instead of inventing an answer. You can set the key later in the dashboard.
3. Click **Apply**. Render builds both Docker images, provisions Postgres and Key Value, injects `DATABASE_URL`, `REDIS_URL` and the API's private-network address, then deploys. The first build takes several minutes.
4. When the Blueprint finishes, open the **`pitstop-web`** service — its `https://pitstop-web-xxxx.onrender.com` URL is the app. Register an account and use it.

Nothing else is required: `DJANGO_SECRET_KEY` is generated by Render, the database and cache URLs are wired from the Blueprint references, media storage is set to `database`, and the BFF finds the API through `API_PROXY_URL=http://$(API_HOSTPORT)` over the private network.

### What you do **not** configure

- **`APP_ORIGIN` (frontend):** the BFF falls back to the service's own `RENDER_EXTERNAL_HOSTNAME` at runtime. Set it explicitly only when you attach a custom domain.
- **`ALLOWED_HOSTS` (backend):** Django already trusts its own `RENDER_EXTERNAL_HOSTNAME`, and `TRUST_PRIVATE_NETWORK_HOST=1` lets the BFF's private-network calls pass host validation (single-label internal hostnames are rewritten to the public hostname — public host checking stays strict).
- **CORS / upload tickets:** the browser talks only to `pitstop-web` (same origin). Uploads up to 7 MiB images / 15 MiB audio-video stream through the BFF; `NEXT_PUBLIC_DIRECT_API_URL` and the Vercel-style ticket flow are not needed here.

## 2. Post-deploy smoke test

Free web services spin down when idle, so the first request after a pause can take ~a minute (Render shows a loading page). Wait for both services to report **Live**, then:

1. `https://pitstop-api-xxxx.onrender.com/health/live/` → `{"status": "ok"}` (process alive).
2. `https://pitstop-api-xxxx.onrender.com/health/ready/` → 200 (Postgres and cache reachable).
3. Open the `pitstop-web` URL → register → you land in the workspace.
4. Create a session, answer the intake questions (symptom, vehicle, year, onset).
5. Upload a small JPEG/PNG attachment → it appears in the conversation; reload the page and re-open it → the bytes are still served (proves database-backed media survives restarts).
6. With a Gemini key set: request diagnosis → a summary with confidence appears; without a key: `ai_not_configured` is returned, as designed.
7. Request a booking with a future date/time → status **pending** (a pending booking is not a confirmed appointment).
8. Log out, log back in → cookies and history behave; wait 15+ minutes idle and retry → both services wake up.

Record the real URLs and results; do not treat a successful Blueprint apply alone as a verified deployment.

## 3. Free-plan limits (read before demoing)

These are Render's documented free-instance behaviors, verified against [render.com/docs/free](https://render.com/docs/free) in September 2026:

- **Spin-down:** a free web service stops after **15 minutes** without inbound traffic; the next request takes about a minute to wake it. The frontend waits on the backend, so a fully cold stack can need two sequential wake-ups. The browser client already shows retryable "backend may be waking up" messaging.
- **750 free instance-hours per workspace per month:** spun-down services don't consume hours, but **two** always-warm web services would need ~1,490 hours and exhaust the quota — do not run external uptime pingers against both services.
- **Free Postgres expires 30 days after creation.** After that the instance is deleted. Before the deadline, export a dump (below) and create a new free database (or upgrade), then point `DATABASE_URL` at it. All application data *and uploaded media* live in this database.
- **Ephemeral filesystem:** anything written to local disk is lost on restart/redeploy — that is why `MEDIA_STORAGE=database` stores uploads in Postgres rows (`chatbot_storedobject`), capped at 15 MiB per file by upload validation, within the free database's 1 GB.
- **Key Value (Redis) free:** 25 MB, **no persistence** — acceptable because it only holds short-lived throttle counters and replay flags; losing them on restart is safe (daily AI budgets are enforced transactionally in Postgres, not Redis).
- **Bandwidth/build minutes** count against workspace quotas; exceeding them can suspend free services for the month.
- Free instances are shared-CPU and slow; this is a demo/evaluation topology, **not** a production SLA.

## 4. Backups and data lifecycle

- **Database (includes media):** Render's free Postgres has no automated backups. To export manually, temporarily allow your IP in `pitstop-db` → Settings → IP Allow List (the Blueprint ships it private-network-only), then:

  ```bash
  pg_dump "postgresql://pitstop:PASSWORD@HOST/pitstop" -Fc > pitstop.dump
  # Restore into a fresh instance:
  pg_restore -d "postgresql://pitstop:PASSWORD@NEWHOST/pitstop" --no-owner pitstop.dump
  ```

  The dashboard's **Connect** menu shows the external connection string once access is allowed. Remove the allow-list entry afterwards.
- **Media** needs no separate archive in this topology: attachments are rows in the same database (`MEDIA_STORAGE=database`), so one dump covers everything.
- Before the **30-day expiry**, either export + recreate the free database or upgrade it to a paid plan (paid Postgres does not expire and gains automated backups).

## 5. Optional next steps

- **Gemini AI:** `pitstop-api` → Environment → set `GEMINI_API_KEY` (backend only; never a frontend variable) → save & redeploy. `GEMINI_MODEL`, `AI_USER_DAILY_CALLS` (default 20/day/user) and `AI_GLOBAL_DAILY_CALLS` (100/day) are already set in the Blueprint; also configure provider-side spend limits.
- **Custom domain:** attach it to `pitstop-web`, then set `APP_ORIGIN=https://your.domain` on `pitstop-web` (exact origin, no trailing slash) so the production Origin check matches.
- **Upgrade path:** moving `pitstop-api` to any paid plan unlocks persistent disks and pre-deploy commands; you can then switch `MEDIA_STORAGE` to `filesystem` + disk or to S3-compatible object storage. Migrations keep working unchanged (`start-render.sh` or a real `preDeployCommand`).
- **Scaling note:** `start-render.sh` runs `migrate` in the single web instance before Gunicorn starts — correct for one free instance; do not run multiple instances of it concurrently without moving migrations to a pre-deploy job.

## 6. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| First request hangs ~1 min, HTML loading page | Free service spinning up. Retry; expected after 15 min idle. |
| `pitstop-api` deploy fails at startup | Check logs for migration errors; the free DB may have expired (30-day limit) — recreate it. |
| 503 `upstream_unavailable` in the UI right after deploy | Backend still cold/building; also verify `pitstop-web` → Env shows `API_PROXY_URL` resolved to `http://pitstop-api-xxxx:10000`. |
| 400 `DisallowedHost` in API logs | `TRUST_PRIVATE_NETWORK_HOST` was removed, or the request used an unexpected public hostname. |
| Diagnosis says `ai_not_configured` | `GEMINI_API_KEY` is empty — by design; set it to enable AI diagnosis. |
| Upload rejected | Content is really validated (Pillow/ffprobe): image ≤7 MiB and matching its declared type, audio/video ≤15 MiB and ≤60 s. |
| Rate-limited (429) | Defaults: 120 req/min/user general, 20/min AI, 30/hour uploads, 10/min auth. Respect `Retry-After`. |

## How it differs from the other documented stacks

- [Vercel + Render + Supabase + Upstash](VERCEL_RENDER.md) — the earlier assignment variant; kept as an alternative. It needs three extra provider accounts, direct-to-backend upload tickets and S3-signed media redirects. This all-Render Blueprint needs one account and no ticket/CORS plumbing (uploads stay same-origin through the BFF).
- [Single-host Compose stack](README.md) — Caddy + Next.js + Gunicorn + Postgres + Redis on your own server, with persistent media volume.

Local verification of this topology is recorded in [HOSTING_VERIFICATION.md](../HOSTING_VERIFICATION.md); a real account-owned deployment and its smoke test remain yours to run.
